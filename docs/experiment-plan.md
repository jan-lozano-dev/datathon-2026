# Prioritized experiments after the baseline audit

The first optimization to implement is a **small, conservative deterministic solver for arithmetic and ratio templates, with exact numeric option matching and abstention**. It can use only the guaranteed text and available options, runs offline with the standard library, and avoids adding model tokens. Build and select its rules on training examples. Do not hard-code validation IDs, values or answers. No optimization was implemented during this audit.

The reproduced original baseline is 65/281 = 23.13% on the local English validation set, equal to always-D. It has 216 errors, including 62 on inputs with five options, text-only metadata and no detected corruption. The inspected ratio and cancellation-equation cases are independently solvable but receive wrong letters. This establishes useful solver targets; it does not establish that the language model specifically made arithmetic mistakes.

All benefit ranges below are **planning hypotheses in absolute percentage points**, not measured improvements or confidence intervals. They assume precision-first implementation on the present input distribution; unseen-test effects may be zero or negative. Hardware latency changes must be measured on the UNO Q.

The accuracy ranges are prioritization estimates, not additive. Use `coverage × change in accuracy on routed cases` to set realistic expectations. For example, covering 5% of cases at 90% rather than 23% accuracy would yield about 3.35 points **if** those assumptions held. Neither coverage nor solver precision has been measured yet.

## Concrete first implementation

1. Create a separate solver module returning a candidate value, recognized template, and an abstention reason. Start with a narrow ratio/percentage family. Add another template only after inspecting its training errors. Avoid unrestricted `eval()` and generated Python.
2. Parse numeric options conservatively: decimals, decimal commas, simple fractions, ratios and supported units. Require exactly one numerically matching answer. Missing, ambiguous, duplicated or apparently damaged choices cause abstention. Do not silently repair missing digits from guesses.
3. Route only when every required quantity and relationship is explicitly recognized. Otherwise call the unchanged baseline. Preserve the official `predict.py` CLI and one-letter output. Do not depend on `label`, `topic`, `text_only`, school level, an English translation lookup, or access to hidden images.
4. Develop against training examples and synthetic paraphrases, including counterexamples that must abstain. Deduplicate training against the chosen evaluation cohort. Record coverage, routed precision, abstention reasons, false routes, fixed cases and regressions. This phase's inspection is diagnostic; it is not a license to fit rules to those 26 validation errors.
5. Freeze the implementation; run the same 50 development keys in the manifest. Compare with the original snapshot using `python3 -m benchmark compare`. A gain of one or two answers on 50 is weak evidence. Keep logs even if results worsen.
6. Run the separate final manifest only after selection, then full validation for descriptive reporting. These existing 231/281 cases have already been exposed by past experiments; obtain a fresh grouped holdout before claiming independent generalization. Do not optimize against its labels after opening it.
7. Repeat on the Arduino with pinned weights/server flags, no concurrent requests, the same ordering, and documented cache conditions. Check peak memory with all required services running, cold start separately, maximum per-problem wall time under 60 seconds, exactly one A–E answer and repeatability. Laptop timings do not satisfy this gate.

Before any RAG experiment, inspect `results/baseline-audit/dataset-audit.json`, eliminate confirmed repeated tasks across splits from the retrieval corpus, and run `benchmark check-index`. An identical statement can carry a different correct letter because choices were permuted; never retrieve a validation answer through another ID or translation.

## Experiments not completed in this phase

- UNO Q development/full validation, RAM peak, thermal/cold-cache measurements and offline board demonstration: no board connection discovered or supplied.
- Original RAG evaluation: embedding server on 8082 and retrieval index absent; embedding weights absent locally.
- Non-English evaluation and translation leakage counts in a multilingual local corpus: local prepared data is English only.
- Broad OCR precision/recall study, exhaustive semantic deduplication, and precise arithmetic-versus-reasoning causal attribution: current flags and purposive inspections cannot estimate these reliably.
- Any new optimization's accuracy benefit: none of the five hypotheses was implemented or evaluated as a new variant here.
