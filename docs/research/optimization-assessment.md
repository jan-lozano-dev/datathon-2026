# Paired assessment of the two answer-label changes

Historical assessment of the Qwen3.5 baseline, before the program-of-thought pipeline. See [reason.md](../reason.md) for the delivered version. Commands below run from the repository root.

## Setup

Tested all 281 unique questions in `data/val.jsonl` on the local llama-server, using the current model and prompt. The two factors were (1) the A–E letter-prior calibration estimated from 20 training questions with five option rotations each, and (2) answering D without a model call when OCR found no options. Calibration remains disabled in the default solver; the no-options route is enabled.

`assess_optimizations.py` called the model once per question and derived all four answers from the same response. This removes differences between separate model runs from the main accuracy comparison. For option-bearing questions it requested A–E log probabilities; all five scores were available for all 167 such questions. The per-question CSV is in ignored `results/optimization-paired.csv`.

| Off | On | 69 | 24.6% | +4 (+28 gained, 24 lost) | −3.6 to +6.4 points | 0.678 |

Always answering D gets 65/281 (23.1%). The current default route exceeds that by only four questions (11 gained, seven lost; exact paired p = 0.481). These validation results do not establish an accuracy improvement for either change or their combination. The calibration changed 105 letters but gained only two correct answers overall.

The `text_only` split suggests the changes may help image-dependent questions and hurt text-only questions. This was discovered on validation data and is exploratory; do not turn it into a new rule without an independent check. All gains occurred in the first 200 validation questions used during earlier iteration: baseline/calibration/route/both were 45/47/49/51 correct there. On the remaining 81, all four methods got 20 correct. The latter 81 have also been inspected in previous experiments, so they are not a fresh hidden test.

## Workload and latency

The route skips 114/281 model calls (40.6%). In this paired local run, those calls accounted for 113.7 of 293.6 seconds of measured model-call time (38.7%) and 10,521 reported `timings.prompt_n` tokens. The separate production-path `eval.py` run of the current default solver took 177.9 seconds for 281 questions: 0.63 seconds mean, 1.89 seconds maximum, and no 60-second limit violations. The earlier baseline production-path run on the same first 200 questions took 231.8 seconds, versus 121.6 seconds for the route. These are laptop timings. Board latency has not been measured for this comparison; `adb` was unavailable in this workspace.

Calibration requires asking the server for letter log probabilities and an ignored `data/letter_prior.json` generated by `calibrate_letters.py`. Its weak accuracy result does not justify enabling it by default. The route has a clear inference-saving effect, but its accuracy gain is uncertain. The prompt and model remain heavily biased toward A, B, and D: uncalibrated predictions across the 281 questions were A=89, B=56, C=1, D=134, E=1.

## Reproduce

With the local model server running and `data/letter_prior.json` generated:

```bash
python3 assess_optimizations.py
python3 assess_optimizations.py --from-results
```

The first command remeasures all model calls; the second only recomputes the statistics from the ignored CSV. Confidence intervals for accuracy differences use 10,000 paired bootstrap samples with seed 42; p values are exact two-sided McNemar tests. Multiple variants and subgroup patterns were inspected, so these statistics should be treated as exploratory. The current optimization is best characterized as a roughly 40% reduction in model calls with no demonstrated accuracy improvement.
